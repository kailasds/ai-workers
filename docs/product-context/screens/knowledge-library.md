## 0. What Knowledge is
**The library of what TCS knows and what a Worker can be given** — Skills, Domain Specific Languages (DSLs), EVALs, Definition-of-Done rubrics, small models. Everything lives in the control plane and is read through the platform's own service identity ("Nobody signs in twice and nobody leaves for a second product"). It is a **reference library** (no Refresh button). It is *separate from Learning*, which is "a record of change" — what the estate has added. (CONFIRMED, file headers.) See `domain-model.md` for the Knowledge-vs-Learning relationship diagram.

Tabs (labels / one-line scope):

## 1. Skills — `/knowledge/skills`
**Purpose:** browse every Skill; read one in full; write a new one.
**Information (per Skill, `KnowledgeSkill`):** name (key), title, description, category (27 in mock, e.g. architecture, claims, compliance, development, domain-intelligence, engineering, finance, governance, insurance, lending, modernisation, payments, privacy, quality_engineering, risk, security, wealth, other), status (`live`…), version, tags, provenance (internal / external), licence (null = "Internal, no external licence"), skill_type (`capability` | `definition_of_done` — a DoD Skill "defines what done means, rather than how to do it"), pattern, source/target technology ("Converts"), content digest, `assigned_agent_keys`, `worker_count` (how many Workers carry it; the catalogue is **ordered by it**), `group` (engineering | security | compliance | domain, with `grouped:false` for unmapped categories — e.g. ACP's `other` — which must stay visible).
**Registry totals / groups (mock):** Engineering 36 · Security 8 · Compliance 10 · Domain 57 (5 ungrouped) = 111. `partial: true` means a source is missing — "a catalogue missing a source is a different fact from a small catalogue".
**Status chips:** "Published, not yet loadable" = a live Skill with no assigned agent (Compose offers a Skill only to Workers on those agents).
**Detail:** the whole SKILL.md plus companion files (references/templates/rules/evals; a package such as `agent-blueprint` has ~25 files); package file list (`path`, `kind`, `size_bytes`); open any file as text.
**Actions:** search ("What are you looking for?"); filter by category ("Every category"); filter by group; open Skill; open file; **Write a Skill** (wizard); **Revise** an existing Skill.
**States:** loading ("Reading the registry"); "The Skill library could not be read from this platform." / "The Skill registry could not be read."; "Nothing matches that."

### 1b. Write / revise a Skill — `/knowledge/capture` (SkillWizard)
Six steps: **What it is · The body · What it carries · How to judge it · Checks · Who may load it**. "Nothing is published unchecked."
| Step | Field | Required? | Rules |
|---|---|---|---|
| 1 What it is | name (key, lowercase-hyphenated e.g. `tibco-fault-paths`), title, purpose, **use-when** (list of trigger sentences), category, tags | name/title/purpose/use-when required to continue | Name is a key that goes into a package, a path…; "Lowercase, hyphenated." |
| 2 The body | markdown body; optional **Draft it** from pasted expert notes (async job; polled; gives up after 4 minutes: "Nothing came back within four minutes, so the draft was given up on. Your notes are still here — try again, or write the body yourself.") | body > 40 characters | A draft is a proposal: lands in the fields, is checked by the same gates, attributed on screen. **No partial draft**: a generic body published to the registry every Worker reads would be followed. Open questions the notes did not settle are shown, never resolved into the body. |
| 3 What it carries | companion files: path + content (`references/`, `templates/`, `rules/`, a hand-written `skill-card.md` is kept as is) | no duplicate path; path charset "Letters, digits, dots, hyphens, underscores and slashes."; no empty names | "Two files in one package cannot share a path." |
| 4 How to judge it | eval contract: goal; **3–6 dimensions** tuned to this Skill; **hard fails** ("What would make an answer wrong however well it reads?"); eval **cases** (dimension, prompt, expectation, optional hard_fail); optional EVAL ids it answers (frontmatter `recommended_evaluation_ids`) | goal, ≥ 3 declared dimensions, every case complete, weights not over | Judged on dimensions it declares, "not a rubric reached for afterwards" (Skillify). |
| 5 Checks | runs server checks on the **exact bytes that would be written**: structure, contract, duplication (near-duplicate vs registry), **security** (NVIDIA SkillSpector: risk score 0–100, severity, advice, findings with remediation, and **which analyzers did not run** — "Risk 0 of 100 · LOW · Safe · Nothing found" is not a clean bill because three semantic analyzers do not run on a deterministic gate) | `publishable` must be true | Findings are `blocking` or `advisory`. `registry_writable` (can publish at all) ≠ `publishable` (fit to publish). `registry_read:false` = duplicate check saw nothing ("said rather than passed"). Publish quotes `checked_digest`, so a draft edited afterwards is refused. |
| 6 Who may load it | choose agents (proposed list + all) | — | Result: published with `visibility` {loadable, assigned, already, disabled, detail} — `not_loadable` explains why nobody can load it yet. |
**Revising:** opens the registry's own bytes ("rewriting instead of surgically improving" is the named anti-pattern), keeps `from_digest` so a change written against these bytes cannot be applied to different ones; some Skills cannot be revised by the wizard ("not_revisable": it bundles others); `missing_frontmatter` listed. Result "X is revised" / "is published".

## 2. Domain Specific Languages — `/knowledge/languages`
**Purpose:** browse the business vocabulary Workers can be bound to, **by the business hierarchy they belong to** (the same BFSI tree EVAL Playbooks use — "two reads of one tree are two chances to disagree").
**Information:** hierarchy tree "Business hierarchy" with a scope select ("All business areas"); counts "Published / Here / Below"; per language card: name, path ("Payments > Merchant Payments > Card authorisation and acquiring"), version, market, industry, lines of business ("All lines of business" if none), and "Available to Workers" vs "Not yet available to Workers" (a language with no `plugin_slug` is "browsable, not usable"); **Unfiled languages** ("Filed nowhere — Published, but not under any business area"); open a language to see its **graph** (nodes: entities, rules, axioms, metrics, process steps…; edges by type with meaning) and tree sections/items; statistics (mock: axioms 11, metrics 8, entities 15, hybrid rules 6, process steps 11, rule categories 4, individual rules 30, discovery patterns 9, deterministic 21, non-deterministic 3).
**Example (mock):** `payments-cards` — "Card authorisation and acquiring", Global, Banking & Financial Services, LOB: Card Present, Card Not Present, Merchant Acquiring, Issuing; plugin `domain-intelligence-payments-cards`. 10 languages in capture.
**States:** "No domain language is published yet."; `language_catalogue_read:false` = registry unreachable (≠ no languages).

## 3. EVAL Playbooks — `/knowledge/evals`
**Purpose:** every check a Worker can be held to, and how each is decided; drill through the business hierarchy; see what is **assigned vs inherited** at each level.
**Information:** group tabs (engineering | security | compliance | domain with totals and `ungrouped`); for a hierarchy node: Effective / Inherited / Assigned here counts, EVAL list; per EVAL: name, description ("The registry stores no description for this check."), category ("Measured as"), **Required gate** vs **Measured check** (`hard_gate`), threshold (%), weight (%), pass threshold, version, "Applied from" (source node, `is_inherited`), `review_note` ("Regulatory text not yet reviewed" shows on the choice itself); **how it is executed** (`eval_type`: prompt → judged by a model; code/deterministic → "Decided by code, with no model involved"; hybrid → "Code and a model, each scoring part of it"; rule → "Filed as a rule, with nothing stored to run"; statistical → "Computed from the run, as a statistic"; unrecognised keys are named, not shown as an empty card); the rubric / criteria / score range / code; "Read by the Definition of Done" (which DoD criteria read it); **Golden dataset** panel ("View the golden dataset"): package, total vs enabled cases, framework, metric family, `case_pass_score`, integration patterns, and per dimension the cases (id, pattern, run/not run, skip reason). "Four of them are never run" is the kind of fact it exists to show. The case contents do **not** travel (untrusted source, ~109 KB).
Mock catalogue: 121 evaluations (e.g. `qe.ac_traceability` "Acceptance-Criteria Traceability").

## 4. Definition of Done — `/knowledge/dod`
**Purpose:** "What a Worker has to prove before its work counts as done." A tree of **scopes** — root → Worker type → bounded context — each adding criteria; a bounded context may tighten a gate and **never loosen one**.
**Information:** group tabs (Engineering / Security / Compliance / Domain; empty groups explain what such a criterion would be); node counts "Applies here / Stops a release / Added here / Set further down"; per criterion: display name, **metric name** ("Reported as" — the string the adjudicator inside the Worker matches on), method (llm_judge | harness_metric | code_skill | external_tool; "Judged by a model", "Measured by building it"…), availability (AVAILABLE | REQUIRES_TOOL | NOT_IMPLEMENTED; reason "Nothing here can measure this yet."), skill/tool ref, `pass_score`, `delivered_floor`, default threshold (e.g. ">= 85"), gating (**Release gate** vs "Observed, not gating"), "Measured by", "Inherited from", evidence document/paths/scale, **how the number is produced** (steps, rule, code, EVALs read), and **evidence** across all recorded runs (`measured_runs`, `passed_runs`; none recorded ≠ never passed; `evidence_available:false` ≠ nothing has run). Sections "Set further down" and "Defined, not graded". A scope `in_build` reads "Cannot be composed yet".
Mock rubric examples: functional-equivalence (">= 85", llm_judge, gating, AVAILABLE), spec-coverage (>= 85), codebleu-score (no threshold, not gating), code-quality (harness_metric, NOT_IMPLEMENTED), golden-dataset-eval-pass-rate (>= 80), ut-coverage (>= 85, code_skill).

## 5. SLM Farm — `/knowledge/models`
Small language models held locally — deliberately not the gateway catalogue. Shows the **pair**: a domain-taught model beside the general model it was taught from (same size and architecture, so the difference is the domain). Card: label, domain, size ("N parameters"), memory ("About X GB"), weights id, base model, role, note, `pair_base_id`/`pair_finetune_id`. Empty: "No fine-tuned small language model is registered."
